### Measurement notes

- An apparent 3x slowdown after B-20's fix was investigated before acting: an interleaved A/B (lazy vs pre-opened pools, three rounds) showed the same latency within each round (11.6 vs 12.2, 10.7 vs 10.5, 4.5 vs 4.2 ms) and large swings between rounds. Cause: about 44 % background CPU load on the dev machine. Load numbers must come from a quiet machine or CI, with the load noted.
- Board under 100 concurrent users (11 Nov): the single-process Python load client used 100 % of a core while the server used about 35 % and PostgreSQL almost nothing; a second server worker did not raise throughput. The client was the bottleneck; 4 client processes doubled throughput and cut p95 from 185 to 114 ms. Official numbers come from k6 (load-report.md).
- Ruled out with data: event-loop round trip inside uvicorn (0.25 ms), per-request logging (INFO vs WARNING identical), Nagle/delayed ACK (`TCP_NODELAY` made no difference).
- Dev tooling, Windows: stopping a background `uv run uvicorn` stopped the `uv` wrapper but left its Python children running and listening, so a later server failed to bind (exit 3) while requests reached the old process with old settings (a burst of 429s). Proven with the process list (`python.exe ... uvicorn` from the first start still alive). Stop the server process tree, not only the wrapper.
- Login rate limit during manual runs: five screenshot runs as one account within a minute returned 429 on the sixth login. Expected behavior (5/min per IP and email), not a bug; e2e runs use a server with relaxed limits like the pytest server.
- Statement timing on Windows: asyncpg's LoggedQuery.elapsed read 0.00 ms for every statement of a traced join. Cause: it uses time.monotonic(), which ticks every 15.6 ms on Windows, while perf_counter marks showed statements finishing 0.2 to 0.8 ms apart. The lab reports the perf_counter gap between statements (ADR-040).
- Load test client, 12 Nov: the first local L-B run reported 74 stampede joins and 6 creates as neither 200 nor 409. The access log showed all of them were `503 busy` (50 simultaneous writers against the in-flight cap of 30), the designed overload answer with `Retry-After`. The k6 script treated it as a failure where a real client retries with the same key, so `loadtest/lib.js` gained `postAction` (retry 503 after Retry-After with the same Idempotency-Key, counted as `busy_retries`). Not a server bug; the same run had exactly one winner in each of 12 stampedes, 50 SSE streams with 36 to 37 team events each, and clean invariants.
